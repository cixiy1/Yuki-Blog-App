
## 项目约定
- App 名：仓库/工程名 **Yuki-Blog App**，应用显示名 **Yuki Blog**（全英文显示），Dart 包名 yuki_blog_app，应用 ID com.yiyu14.yuki_blog_app；GitHub 仓库 cixiy1/Yuki-Blog-App（公开）。
- 发版流程：改 pubspec version → Conventional Commits 提交推送 → `git tag vX.Y.Z && git push origin vX.Y.Z`，GitHub Actions 自动测试+构建 APK 并发 Release；App 内更新弹窗读该 Release。
- **固定签名（铁律）**：release 一律用 `android/key.properties` 指定的固定 keystore——**签名参数全部由用户填写，我不得代拟任何口令/别名/证书信息**（模板 `android/key.properties.example`；生成密钥库 `tool/gen_release_keystore.sh`；导出 GitHub Secrets 用的 base64 + 仓库外备份 `tool/make_signing_secrets.sh`）。未配置时 build.gradle.kts 回退 AGP 的 debug 签名并打警告，但 debug 密钥**每台机器、每个 Actions runner 都各自现生成**，产出的包互相无法覆盖安装（`INSTALL_FAILED_UPDATE_INCOMPATIBLE`），App 内更新会直接失效。keystore + 口令丢失＝永远无法再发可覆盖升级的版本，必须有仓库外备份。核对签名：`apksigner verify --print-certs <apk>`，或 `cd android && ./gradlew :app:signingReport`（逐变体列出实际取用的 keystore）。临时测试密钥不得留在 `android/` 下。

- **Git 日志维护**：每个实质性开发节点（新功能 / 修复 / 重构 / 改名）都要及时单独提交，用 Conventional Commits 规范（feat/fix/docs/chore...），不要攒一堆改动混成一个提交；完成即推送 GitHub（cixiy1/Yuki-Blog-App）。
- **双端同步点（改一处必须改两处）**：① 关键词词表 App `lib/features/schedule/widgets/keyword_highlight.dart` 的 `kwMap` ↔ 博客 `src/components/widget/ClassSchedule.astro` 的 `TT_KW_MAP`；② 标注解析与档位 `parseAnnotations + sentenceTierOf + buildKeywordSpans` ↔ `ttParseMarks + ttSentTierOf + hlLog`；③ 更新历与通知面板的布局顺序；④ 数据文件 `assets/data/schedule-2615.json` ↔ 博客 `public/assets/data/schedule-2615.json`（**必须两份同步**）。改完用「抽 astro 函数到 node 跑用例」+「Dart/JS 分档对拍」的方式对齐行为。
- **文字高亮的定位（铁律）**：重点**不写死、也不靠算法猜**。每次有新信息入库（新通知 / 新更新历），必须**先读一遍内容再逐条标注**，标出哪几段值得看；固定词表只负责词类配色，锚点算法只做未审阅内容的兜底。
- **标注语法（写在正文里，渲染前整段剥离）**：`{{…}}` 必看 core ｜ `[[…]]` 关注 key ｜ `((…))` 一般（显式压档）。规则：**整段只要出现过标注即视为「已人工审阅」，全部以标注为准**（没标的句子就是一般，算法不参与）；**整段一个标注都没有才回退算法兜底**。括号不成对时按原文保留。正文里不要出现裸的 `{{` / `[[` / `((`（`"offDays": [[4,5]]` 这类 JSON 结构符号不进解析器，无妨）。
- **标注范围与例外**：覆盖「人工撰写的正文」= `meta.changelog` 条目的 `content` + `notices` 的 `text`。**例外：「本周调整」面板的文案是 resolver 运行时用 `「课程名」+ note` 拼出来的，无法内联标注，因此整层关掉「定档」——不铺句子底纹、不加句首竖条、不按档位加粗，只保留词表着色**（App: `buildKeywordSpans(..., tiered: false)`；博客: `hlLog(c.txt, true)`）。理由：每一行本来就都是「这周要处理的事」，没有筛选意义，叠底纹纯是噪音（实测 85 条里 83 条带高亮、一行常四五个档位）。
- **长内容铁律（用户 2026-10-15 明确）**：凡是「一段话」级别的**信息型正文**——通知、更新历、本周调整、课程详情里的调整说明，以及**以后新增的任何长文展示面**——**一律接入这套高亮，不留纯文本角落**。分档口径：能内联人工标注的走三档（必看 / 关注 / 一般）；运行时拼出来的（如「课程名 + 调整说明」）只走词表着色（App `tiered: false` / 博客 `hlLog(x, true)`）。纯 UI 状态提示（离线提醒、无课横幅、图例）不算长内容，不接。
- **高亮密度铁律**：底色只留「必看」一档、加粗只留「人工标注」；关键词只用「着色 + 同色划线」，不套色块、不描边、不统一加粗。词表只回答「这是什么词」，加粗/底色只回答「值不值得看」，两层职责不重叠。标注本身每条至多 1 处 `{{}}` + 1 处 `[[]]`，讲工具本身与历史条目一律 `(( ))` 压档。
- **公开仓库安全**：`cixiy1/Yuki-Blog-App` 是公开仓库，班级事务个人材料（`/材料/`，如入党谈话内容）已加入 `.gitignore`，不得提交；新增此类本地材料时先确认被忽略，避免 `git add -A` 误推。
- **本机网络坑**：本机 HTTP 代理（`127.0.0.1:60651`）对 GitHub 是**选择性抽风**——常常同一时刻 `yiyu14.top` / `baidu` / `github.com/` / `api.github.com/` 都是 200，只有 `github.com/<repo>.git/info/refs?service=git-receive-pack` 间歇返回 000（连重试几次后就 401，说明其实是通的）。**别一看到 000 / 502 就判定断网**：先用 `curl -s -m 15 -o /dev/null -w "%{http_code}" "<该 info/refs 地址>"` 探一下，再循环重试 `git push`（通常 1～10 次内成功）。`flutter test` 需 `env -u HTTP_PROXY ...` 绕过代理（否则 flutter_tester 本地 WebSocket 被代理劫持）。
- **判断推送是否真失败**：`git push | tail` 的退出码取的是 `tail`，`&&`/`grep` 判断会误判。改用 `git status -sb | head -1` 看有没有 `[ahead N]`——没有即已推送成功。
